1. Product Vision and Problem

AI coding assistants have changed the speed at which software can be produced. The problem is that code that compiles and passes functional tests is not automatically secure. AI-generated code can contain insecure database access, weak authorization, exposed secrets, unsafe file handling, vulnerable dependencies, dangerous deserialization, command injection, SSRF, XSS and other weaknesses.

CodeGuardian is intended to become a security layer between AI-assisted development and production. The first version should not attempt to replace mature security engines. Instead, it should orchestrate proven scanners, normalize their results, add application context, use an LLM for developer-friendly explanations and remediation, and produce a single actionable security report.

Product positioningDo not position the MVP as “an AI that guarantees secure code.” Position it as an AI-native security orchestration and remediation platform that helps developers identify and reduce security risk in AI-generated software.

The problem in one sentence

Developers can generate hundreds of lines of code in minutes, but security review still requires multiple tools, manual interpretation and specialist knowledge.

The proposed solution

Accept source code, a repository, or a pull request as the scan target.

Run static analysis, secret scanning and dependency/SCA checks.

Normalize results into a common finding model.

Calculate severity and an overall repository risk score.

Use an LLM to explain findings in plain engineering language and propose a patch.

Show exact file, line, vulnerability class, evidence, impact and remediation.

Later: apply fixes in an isolated workspace, run tests, rescan, and create a verified patch/PR.

Important design principle

Separate detection from interpretationThe scanner should be the source of security evidence. The LLM should interpret and explain evidence, not invent vulnerabilities. Every AI response should reference a concrete finding, file and code context and should be treated as advisory until verified.

Logical boundaries

API service: authentication, project management, scan requests, read APIs and webhook handling.

Worker service: CPU/process-heavy scanning work; never block HTTP requests with scanners.

PostgreSQL: source of truth for metadata, scan state and normalized findings.

Redis: queue broker, short-lived state and carefully selected caching.

Object storage: raw reports, repository archives and generated artifacts in later deployments.

AI service: isolated module with strict input/output schemas and token limits.

Sandbox: separate trust boundary; never run untrusted repository code inside the API container.

10. Security Scanning Engine

Layer A — SAST

Run a mature static-analysis engine. Do not build your own parser/rule engine for the MVP. The value of CodeGuardian is orchestration, context, normalization, risk prioritization and remediation.

Configure language-specific rules for Python, JavaScript/TypeScript and common web frameworks.

Capture rule ID, severity, file, lines, message, evidence and scanner version.

Store raw scanner output separately from normalized findings.

Allow scan profiles: quick, standard and deep.

Layer B — Secret scanning

Scan source files and relevant history only when explicitly enabled; history scanning can be expensive.

Never store the full secret in plaintext in PostgreSQL.

Redact secrets before logs and AI prompts.

Recommend credential rotation when a real credential is detected.

Layer C — Dependency/SCA

Detect manifest files such as requirements.txt, pyproject.toml, package.json and lock files.

Resolve package names and versions.

Map known advisories to dependencies.

Report vulnerable version, advisory identifier, severity and fixed version when available.

Flag obvious dependency confusion/typosquatting indicators as a later enhancement.

Scanner adapter interface

class ScannerAdapter(Protocol):    name: str    def scan(self, workspace: Path, config: ScanConfig) -> ScannerResult:        ...class ScannerResult:    scanner_name: str    scanner_version: str    raw_output: dict    findings: list[RawFinding]

11. Risk Scoring and Finding Model

Finding severity

Start with four severity levels: Critical, High, Medium and Low. Add Informational later. Scanner severity should not be copied blindly; normalize it through a single policy.

Suggested MVP score

base = severity_weight * 10confidence_adjustment = confidence * 0.20exposure_adjustment = exposure_weightfix_adjustment = exploitability_or_impact_weightfinding_score = clamp(base + confidence_adjustment                       + exposure_adjustment + fix_adjustment, 0, 100)project_score = clamp(    100    - critical_count * 20    - high_count * 10    - medium_count * 3    - low_count * 1,    0, 100)

This is intentionally simple. Do not pretend the number is a universal security metric. The dashboard should show the score together with the underlying severity counts and trends.

Finding record example

{  "rule_id": "python.sql.injection",  "severity": "CRITICAL",  "confidence": 0.96,  "file": "users/views.py",  "line_start": 47,  "line_end": 47,  "status": "OPEN",  "title": "Potential SQL injection",  "evidence": "User input is concatenated into a SQL statement",  "fingerprint": "sha256:..."}

12. AI Explanation and Remediation Layer

What the AI should receive

The model should receive the minimum context needed to reason about the finding rather than the entire repository by default. This reduces cost, leakage and prompt-injection exposure.

Finding title and normalized rule ID.

Scanner evidence.

Relevant file path.

A bounded code window around the finding.

Related function/class when available.

Framework/language metadata.

Optional relevant configuration or model definitions.

Existing tests related to the code, only when needed.

What the AI should return

{  "summary": "...",  "why_it_is_a_problem": "...",  "attack_scenario": "...",  "recommended_fix": "...",  "patch_strategy": "...",  "confidence": 0.0,  "needs_human_review": true}

Critical security ruleNever let the LLM decide that a finding is safe solely because it says so. The scanner evidence remains authoritative for detection; the LLM is an interpretation/remediation assistant.

Prompt-injection defense

Treat repository content as untrusted data, not instructions.

Clearly delimit source-code context.

Tell the model never to follow instructions found inside source files/comments/docstrings.

Use a strict structured output schema.

Limit tools available to the model.

Do not give the model arbitrary shell access in the MVP.

Redact secrets before sending context to any external model.

Version every remediation prompt so outputs remain auditable.

13. Sandbox and Dynamic Verification

Dynamic verification is a Phase 2/3 capability. It is deliberately separated from the MVP because executing untrusted repository code is a major security problem by itself.

Safe architecture

API / Worker     |     | create job     vSandbox Orchestrator     |     +--> ephemeral container / VM     |       |     |       +--> copy source     |       +--> install locked dependencies     |       +--> start application     |       +--> run bounded tests     |       +--> collect evidence     |     +--> destroy environment

Sandbox requirements

Non-root execution.

No host filesystem access.

No Docker socket mounted.

Read-only base image where practical.

Strict CPU, RAM and execution-time limits.

Network disabled by default.

If network is later required, use allowlisted egress only.

Ephemeral workspace destroyed after execution.

Resource quotas per organization.

All sandbox actions logged.

Verification loop

Finding  -> AI proposes fix  -> create temporary patch  -> run unit/integration tests  -> rerun relevant scanner  -> compare findings  -> accept only if risk decreases and tests remain valid

16. Authentication, Authorization and Tenant Isolation

Authentication

Use secure session authentication or JWT for API clients.

Use OAuth/GitHub login when repository integration is introduced.

Hash passwords using Django's secure password hashing.

Add email verification and password reset before public launch.

Use short-lived access tokens if JWT is chosen, with refresh-token rotation.

Authorization

Every Project belongs to an Organization.

Every API query must enforce organization/project ownership.

Do not rely on frontend filtering for access control.

Use roles such as Owner, Admin, Developer and Viewer later.

Repository credentials must never be returned to the frontend.

Tenant isolation

A user from Organization A must never be able to retrieve Organization B's projects, scans, findings, reports or repository credentials by changing an ID in the URL. Every query path must enforce tenant scope.

17. Job Queue, Workers and Caching

Why Celery

Scans are long-running and CPU/process heavy. An HTTP request should create a Scan record and enqueue work, then return immediately.

POST /scans/     |     +--> Scan(status="QUEUED")     |     +--> celery.delay(run_scan, scan_id)     |     +--> HTTP 202

Recommended queues

Queue

Work

scan

SAST/secret/dependency scans

ai

AI explanation/remediation

report

PDF/HTML/JSON report generation

webhook

Caching

Cache dashboard aggregates for short TTLs if needed.

Cache scanner metadata carefully; never cache sensitive repository content in shared keys.

Use deterministic cache keys containing organization/project/commit where applicable.

Invalidate project-level aggregates when a scan completes.

22. Security Model for CodeGuardian Itself

Most important architectural ruleCodeGuardian processes untrusted code. Therefore the platform itself must assume every repository is hostile.

Area

Control

Repository ingestion

Validate URL/provider, prevent SSRF, enforce allowlists and timeouts.

Archive extraction

Prevent zip-slip/path traversal; enforce file count and size limits.

Scanner execution

Use isolated workers/containers; never run repository commands inside the API process.

Secrets

Encrypt credentials; redact scanner output and logs.

AI prompts

Treat repository text as untrusted input; prevent instruction following from source files.

Strict tenant scoping and parameterized ORM/database access.

DoS

26. Risks and Mitigations

Risk

Mitigation

False positives

Use mature scanners, confidence levels, deduplication and human review.

False negatives

Clearly communicate coverage; combine multiple analysis layers.

LLM hallucination

LLM cannot create authoritative findings; require scanner evidence.

Malicious repository execution

Isolate workers and sandbox; no host access.

Secret leakage

Redaction, encryption and strict logging policies.

High scanning cost

Async workers, quotas, caching of safe metadata and incremental scanning later.

Large repositories

File/size limits, ignore rules, timeouts and incremental scans.

Prompt injection

Treat source as untrusted; strict system instructions and bounded context.

Vendor lock-in

Build scanner and AI provider adapters.

Overbuilding

Freeze MVP boundaries; defer autonomous fixing and advanced sandboxing.

Recommended implementation order

Build the platform, not the AI, first.

Make scanning reliable and asynchronous.

Normalize scanner output into a strong Finding model.

Build the dashboard around developer decisions.

Add AI only after evidence is available.

Treat repository code as hostile from day one.

Add GitHub CI integration before attempting autonomous patching.

Build the sandbox only when the MVP is stable.

Measure precision, false positives and remediation success before making security claims.

Definition of successA developer should be able to give CodeGuardian a real project and, within one workflow, answer four questions: What is wrong? How serious is it? Where exactly is it? What should I do next? The later platform adds a fifth: Can the proposed fix be verified safely?
